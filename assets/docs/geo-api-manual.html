京东云 GEO-API 使用手册#

企业级“一客一案”解决方案 · 客户接入版 · 2026-11-13
面向品牌商、KA 客户的产品与技术团队。

通过京东云 GEO API，您可以在自己的业务系统中完成 Step 1 拓词 → Step 2 诊断 → Step 3 立项 → Step 4 监测：提交品牌、问题和服务配置，查看处理进度、诊断结论、项目效果与证据，逐步形成企业自己的 GEO 工作台。

适用范围：第1—8章介绍现有 /openapi/v1 接口的接入方式，第9—10章介绍企业增强的规划能力。/openapi/v2 尚未发布，须在京东云交付对应接入地址与功能授权后使用。接口与模型按账户实际开通范围调用；所有业务数据和 ID 示例均为模拟值。

接入规则：优化项目审核通过后，先通过 M01 按 project_id 找到对应项目；此时 status=pending、review_status=approved，客户再调用 P03 正式立项，成功后进入 running。立项与监测使用同一个 project_id，监测查询直接传入原值。

1. 使用前准备#

1.1 申请开通与获取接入信息#

请联系京东云项目对接人，获取以下接入信息，并确认账号、模型、服务范围及资源额度。

1.2 推荐接入架构#

客户页面调用客户后端；客户后端持有 GEO 凭证、缓存令牌、记录业务 ID，并调用京东云 GEO。京东云承担任务编排、诊断、运营审核、优化执行和数据生产，调用结果经客户后端返回页面。

客户后端至少保存：客户自己的 case_ref、拓词 job_id、诊断 task_id、服务 project_id、提交与立项幂等号、授权范围以及请求结果。case_ref 是建议客户自行建立的“一案”编号，不是现有 v1 接口已接受的请求字段。不要把它直接追加到现有请求体。

1.3 获取令牌#

调用 POST /auth/token，通过 Basic 头携带客户凭证，JSON 中携带系统用户账号密码。成功响应为 code/message/data；令牌放在 data.access_token。

BASH
# GEO_BASE_URL 仅配置一次，值包含 /openapi/v1；不要再重复拼接该前缀。
export GEO_BASE_URL='https://l.geo.jdcloud.com/openapi/v1'
# CLIENT_ID、CLIENT_SECRET 由客户密钥系统注入。
# credentials.json 在客户后端安全生成，内容见下方 JSON，勿提交到代码仓库。
curl --request POST "$GEO_BASE_URL/auth/token" \
  --user "$CLIENT_ID:$CLIENT_SECRET" \
  --header 'Content-Type: application/json' \
  --data-binary @credentials.json
JSON

  "username": "your_username",
  "password": "your_password"
}
JSON
{
  "code": 200,
  "message": "success",
  "data": {

令牌固定有效30天，没有 Refresh Token。同一 client_id + 系统用户 再次登录会立即使旧令牌失效。请由客户后端集中换取和共享令牌；多实例使用互斥更新，避免每次页面刷新或每个实例自行登录。遇到401先确认是否已被其他实例轮换，再统一更新；不要无限重复登录。

2. 使用流程概述#

2.1 四步业务流程#

步骤客户页面完成什么京东云完成什么输出与下一步
Step 1 拓词填写品牌、品类、卖点和种子问题；筛选候选问题异步生成认知、场景、对比、决策四类意图词job_id、items；客户选词后提交诊断
Step 2 诊断选择问题、平台、指标与次数；确认资源消耗预估、锁点、实际采集、指标分析与选词建议诊断 task_id、摘要及分问题/模型结果
Step 3 立项提交服务范围；优化项目经 M01 查到审核通过后调用 P03创建与审核项目；优化项目在 P03 成功后启动同一 project_id；审核通过为 pending + approved，立项成功为 running
Step 4 监测直接使用立项返回的 project_id 查询进度、指标、回答原文与信源持续采集、优化交付、生成数据效果与证据；支持下一轮拓词/诊断形成迭代

优化项目通过 P02 送审后，由客户后端调用 M01 查询服务项目列表，并以 P02 返回的 project_id 匹配条目。审核通过时，review_status=approved，执行状态仍为 status=pending；客户随后调用 P03 正式立项，成功后 status=running。查询状态本身不会触发启动。

优化项目阶段statusreview_status客户下一步
P02 已提交、审核中pendingpending_review继续查询 M01，按 project_id 匹配项目
审核通过、等待正式立项pendingapproved调用 P03，传入原 project_id 和独立 initiation_request_id
P03 正式立项成功runningapproved以同一 project_id 调用 M04—M07 查询监测结果

持续监测项目沿用监测服务流程：提交前完成服务授权和资源确认，提交后查看返回状态或 M01/M02；P03 用于优化项目。部分审核通过的项目先确认有效范围，再按 P03 的启动条件处理。

2.2 系统交互时序#

提交拓词/诊断只表示任务受理，不代表已完成。客户后端查询状态，完成后查询结果；网页可及时展示已受理、排队、运行、部分成功和失败。持续监测数据的生成频率、开放延迟与查询延迟应分开理解，可以随时查询不代表第三方 AI 回答秒级生成或指标秒级更新。

2.3 对象与 ID 传递#

标识含义来源与类型下游传递
case_ref客户自己的方案编号客户自建字符串；企业增强规划接收关联多轮拓词、诊断及项目；不能向现有 v1 请求强行添加
job_id一次拓词任务T01 返回 string仅传给 T02
task_id一次云侧异步诊断D02 返回 stringD03/D05 查询；P01/P02 的 source_task_id 引用此值

服务项目与监测共用同一个 project_id。本版沿用 P02/P03 的 string 字段约定，M04—M07 的项目标识同步按该类型说明；客户端保存并直接传递服务端返回值。字段名统一使用 project_id。

诊断前无需先创建收费服务项目。T01 的可选关联参数按拓词接口本身的字段约定执行，最小接入可省略；生成的候选词不会自动写入项目词库。审核后项目范围如发生变化，需要保留原申请、最终通过范围及审核记录。

2.4 选择接入方式#

现有接口按各步骤分别接入；托管聚合方式规划提供任务创建、数据查询、诊断结果和报告获取四个业务入口。鉴权、开通配置和自助拓词按实际场景接入。

接入方式适用场景客户实际接入
现有接口接入客户需要掌握四步表单与操作细节，优先复用现有服务第3—7章接口；M01 确认审核通过后调用 P03，后续监测直接使用同一 project_id
托管聚合接入（规划）客户提交已选问题与服务配置，京东云托管诊断、审核、启动及报告N02—N05四个业务入口；鉴权不计入4个，开通配置由交付完成
四步完整自助页面同时需要自助拓词、选词、修改重提、延期等操作四个聚合入口之外增加 T01/T02及需要的变更 API；不能承诺总共只需4个

托管方式仍应由客户明确授权启动策略和服务范围。诊断任务不能自动升级成收费优化；合同或商务未就绪时，不执行优化。

4. 最小接入单元#

4.1 定义一个可验收的最小业务单元#

推荐首次联调使用：1个授权账号、1个品牌、1个客户方案、1个有效问题、1个授权模型、1次诊断、1个服务项目、1个可用监测日期。这只是技术联调最小粒度，不是商业起订量。

示例：品牌“示例品牌”、品类“空气净化器”、问题“小户型空气净化器怎么选”、模型 deepseek、诊断指标 brand_visibility + top_rank、诊断次数1。优化项目周期使用现有 v1 接口的 duration_months=1，两个收费 KPI 对应的预估为1000点；最终以预估响应为准。诊断预估为 1×1×2×1×0.01=0.02 点。此处点数不等于合同报价。

4.2 现有接口的最小调用链#

以下为优化项目的最小路径，共12种端点（含鉴权），其中拓词/诊断状态和 M01 服务项目列表可能多次调用。可用模型和额度应已开通；平台查询、账户余额、项目详情、信源和充值不计入这个最小集合。持续监测路径省去优化送审等待及 P03，提交前完成服务授权和资源确认。

项目衔接：P02、M01 对应条目、P03 和 M04—M07 使用同一个 project_id。M01 是列表查询，按分页遍历并匹配 items[].project_id，不新增 project_id 请求参数。单页未找到目标项目时继续翻页，不能据此判定审核失败。

诊断与拓词的创建接口没有声明幂等参数。创建后网络超时，先查已保存的返回和业务记录；诊断可用D04辅助排查，任务名不是唯一键，不能据此自动认定同一个任务。未知受理结果先核实，不直接循环重建收费诊断。企业增强规划由N02提供幂等受理能力。

5.3 错误与重试#

HTTP状态含义客户处理
401凭证、用户或Token无效/失效检查共享令牌，再受控刷新；写操作沿用原幂等键
403scope、模块、模型或资源范围不足修正授权，不能通过换ID试探其他客户数据
404资源不存在或不可见检查ID来源及归属；不根据404断言资源从未创建
409状态不允许或幂等键对应不同内容未出诊断结果先查D03；幂等冲突修正业务操作，不盲目重试
422参数、配置、余额等不满足要求展示可修正原因；预估成功也可能因余额变化而创建失败
429登录超限按服务端反馈等待，减少并发登录
500 / 503内部异常 / 鉴权依赖不可用查询可退避重试；无幂等写请求先核实受理情况

处理错误时同时记录 HTTP 状态、响应正文和关联业务 ID。企业增强接口的结构化错误格式见第9章。

登录限流：5分钟窗口内，同一授权方、用户和IP组合最多10次，同一IP最多1000次。T02、D03建议每10秒轮询。业务请求配额与采集、发布时效按开通服务约定执行。

5.4 幂等和副作用边界#

操作已有幂等字段副作用与要求
A04充值request_id同授权方、同键同内容只入账一次；不同内容409
P02服务提交request_id同授权方、同键同内容不重复建项目/锁点；不同内容409
P03启动initiation_request_id正式立项使用独立幂等号；同一次操作保留原值
T01拓词、D02诊断未定义不向原接口添加未声明幂等字段；超时后不能保证安全重试
D01/P01预估、所有查询无写入业务动作预估不锁点；查询不创建新的采集/优化任务

D02结束后按实际成功组合结算，未执行/失败部分释放；P02优化审核前锁点为0，仅通过的收费KPI锁点，免费观察项也随组合审核。点数不足属于422。现有 v1 接口没有给出暂停、取消、退费和执行期修改接口，仅有状态枚举不等于有对应操作API。

8.1 产品能力与可用指标#

8.2 指标读取与显示#

现有诊断的*_rate、信源分布的percentage使用0—100百分数，例如60表示60%。top_rank是排名值，不能作为Top3率使用。未选择的指标、缺失结果与实际测得0分别处理。

8.3 日数据、汇总和缺失样本#

企业增强的日数据包含expected_samples/valid_samples/failed_samples/missing_samples。失败与缺失不补0；样本不足时使用insufficient_samples，与达标或未达标区分显示。

8.4 基线、考核期与达标结果#

信息页面处理

8.5 数据新鲜度和报告冻结#

v2聚合响应应返回：data_as_of（最新纳入的采集时刻）、published_at（聚合发布时间）、data_version、snapshot_id、collection_status。其中collection_status=collecting/partial/complete/failed表示所查询范围的完整性，不等于任务执行状态。现有 v1 接口缺少这些通用字段，页面只能保守展示已知日期，不能虚构“实时更新成功”。

执行完成、数据完成、报告完成和客户验收是不同阶段。最终报告仅在服务范围与实际周期已冻结、末批数据完成或按协议处理、延期窗口关闭后生成。报告冻结data_version/metric_definition_version/assessment_policy_version；补数产生新报告版本，不能静默改变已交付文件。

N06 修改后重新送审#

POST /openapi/v2/service-projects/{project_id}/resubmit · 规划能力。

请求：request_id string必填；expected_version integer必填；review_version integer必填；reason string必填（1—500字符）；configuration object必填（采用7.1优化配置，不含request_id和project_name）。返回原project_id、新review_version/resource_version、review_status=pending_review、submitted_at。

规划限制：仅未启动且部分通过、允许修改的项目可重提；已取消、全部驳回或运行中项目返回409。新轮次使用新request_id，项目ID不变；同次重试不增加轮次。旧轮次审核记录保留，旧事件不覆盖新轮次状态。

N08 提交达标结项#

POST /openapi/v2/service-projects/{project_id}/achievement · 规划能力。

请求：request_id string必填；expected_version integer必填；assessment_data_version string必填；reason string必填（1—500字符）。服务端校验该数据版本属于当前项目、规则有效、合同条件已满足；不能只凭客户端传“达标”直接结束。

仅对已授权的延期执行项目开放。成功返回原project_id、status=completed、completed_at、actual_end_date、data_finalization_status=pending/complete及新resource_version。停止生成后续任务，已在途采集按冻结截止时刻归档；报告继续等末批数据。自然结束与主动达标都不直接代表客户商务验收。

N08以同步结果确认结项操作；后续数据或报告就绪可分别发送data.ready/report.ready通知。

9.3 可选状态与数据通知（规划）#

客户可只使用轮询；Webhook用于缩短页面获知更新的等待。通过开通流程登记HTTPS回调地址和独立签名密钥，不复用访问Token。发送事件最少包含event_id/event_type/occurred_at/resource_type/resource_id/resource_version；数据就绪附data_version，报告就绪附report_id/report_version。不在回调携带全部回答或客户敏感材料。

规划事件：task.updated/project.reviewed/project.updated/data.ready/report.ready。规划请求头：X-GEO-Event-Id、X-GEO-Timestamp（Unix秒）、X-GEO-Signature。签名为HMAC-SHA256，输入为timestamp + "." + 原始HTTP Body字节，签名输出小写十六进制；接收方常量时间比较。每次重试保持业务event_id和Body，重新生成投递时间戳与签名；容许时钟偏差默认建议5分钟，最终由开通配置明确。

客户先验签和资源绑定，再将事件持久化到接收队列/幂等表，成功后返回HTTP200及{"accepted":true}；重复有效事件返回200及{"accepted":false}。按event_id去重，按resource_version拒绝旧状态覆盖新状态。消息可能重复、乱序或早于创建响应；未关联事件先持久化待匹配，不匹配到同品牌其他任务。

规划采用至少一次投递，接收方按event_id去重。投递间隔、重试次数和保留期按开通配置执行；通知失败不影响查询结果，客户可用N03/N05获取当前状态。
